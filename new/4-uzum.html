MarketCore — katta marketplace backend loyihasi

Versiya 1.0 • Sana: 03.11.2026 • Til: O‘zbek • Stack: Go + httprouter + PostgreSQL + Redis + gRPC + RabbitMQ • Maqsad: senior backend engineering amaliyoti

Bo‘limni chap menyudan tanlang yoki Ctrl+F bosing. Qidiruv bo‘limlarni ajratib ko‘rsatadi.
Hujjatdan qanday foydalaniladi? Har bir servisning doimiy identifikatori bor: S01…S15. Har bir biznes oqim F01…; event E01…; texnik qaror ADR-001…; bosqich P0… bilan belgilangan. Keyin “S08 payment_webhook_events” deb qidirsangiz kerakli joyni topasiz. Bu loyiha uchun boshlang‘ich loyiha spetsifikatsiyasi, tayyor kod yoki tasdiqlangan production SLA emas.

00. Eng muhim boshlang‘ich qarorlar

  1. Birdan 15 ta mikroservis yaratmaymiz. Dastlab Go modular monolith; modul chegaralari aniq, keyin eng keraklilari ajratiladi.
  2. Bir seller — ko‘p store — ko‘p product; bir order ichida bir necha seller bo‘lishi mumkin. Bitta customer order bir nechta fulfillment/shipmentga bo‘linadi.
  3. Money — BIGINT minor units (UZS uchun biznesdagi birlikni aniq belgilaymiz; misollarda so‘mning butun birliklari); float ishlatilmaydi.
  4. Stock — on_hand - reserved; checkoutda rezerv, to‘lov yakunida rezervni sotuvga aylantirish; timeoutda release.
  5. To‘lov — tashqi provider adapterlari; callbackga ishonishdan oldin signature/merchant/amount/order tekshiruvi; server-to-server status/reconciliation.
  6. Servislar orasida cross-database FK yo‘q; gRPC yoki event. Event delivery at-least-once, consumer idempotent.
  7. Security — har bir requestda authorization, seller tenant izolatsiyasi, maxfiy ma’lumotlarni minimal saqlash.

05. Biznes oqimlar — F01…F08

F01 — Registration → profile

  1. Auth input validate, email unique, Argon2id/bcrypt hash, user insert + outbox.
  2. UserRegistered eventdan User module profil yaratadi (idempotent).
  3. Email verification va login. User profil yaratilmagan paytda eventual consistency holati UI'da ko‘rsatiladi.

F02 — Seller → Product → Publish

  1. Seller owner do‘kon ochadi, admin tasdiqlaydi.
  2. Product + variant + SKU + price kiritiladi; moderatsiya.
  3. ProductPublished Search indexni yangilaydi; Inventory boshlang‘ich stockni kirim movement orqali qabul qiladi.

F03 — Checkout / Saga (eng muhim)

  1. Customer POST /orders va Idempotency-Key yuboradi.
  2. Order server Product/Promotiondan ishonchli quote oladi; narx, seller, status, delivery va jami summani qayta tekshiradi.
  3. Order pending va item snapshotlarini transactionda yozadi, saga step saqlaydi.
  4. Inventory har bir itemni atomic reserve qiladi; qisman xatoda muvaffaqiyatli rezervlar release qilinadi.
  5. Payment provider intent yaratiladi; customer to‘lovni amalga oshiradi.
  6. Verified payment event → Order confirmed → Inventory reservation commit → fulfillment request. Statuslarni transaction/event bilan idempotent yuritish kerak.
  7. Payment muvaffaqiyatsiz yoki deadline tugasa → saga compensation: inventory release, coupon release, order cancel. Agar payment keyin muvaffaqiyatli kelsa, refund/manual reconciliation qoidasiga o‘tiladi.
Race condition: PaymentSucceeded va ReservationExpired bir vaqtda kelishi mumkin. Bitta order state machine, version/CAS, transaction va reconciliation worker bo‘lishi kerak. “Payment succeeded” avtomatik ravishda “order fulfilled” degani emas.

F04 — Stock reservation

BEGIN;
UPDATE stocks
SET reserved = reserved + $qty, version = version + 1
WHERE warehouse_id = $warehouse_id AND variant_id = $variant_id
  AND on_hand - reserved >= $qty
RETURNING on_hand, reserved;
-- 0 rows: OUT_OF_STOCK; rollback
INSERT INTO stock_reservations(order_id,order_item_id,warehouse_id,variant_id,quantity,status,expires_at)
VALUES ($order_id,$item_id,$warehouse_id,$variant_id,$qty,'active',now()+interval '15 minutes');
COMMIT;

Commit: bir transactionda on_hand -= qty, reserved -= qty, reservation status committed va stock movement. Release: faqat active reservationda reserved -= qty va status released. Ikkinchi chaqiriq hech narsani takrorlamaydi. Lock order bir xil bo‘lishi deadlock ehtimolini kamaytiradi.

F05 — Payment webhook

  1. Provider raw payload, signature/authentication, timestamp/nonce tekshiriladi.
  2. Provider transaction ID va event ID unique; webhook inboxga yoziladi.
  3. Order ID, currency, amount va payment state tekshiriladi; kerak bo‘lsa provider status API orqali tasdiqlanadi.
  4. Transactionda payment update + ledger + outbox; duplicate event no-op.
  5. Providerga belgilangan protokol bo‘yicha tez ACK; reconciliation job nomuvofiqliklarni aniqlaydi.

F06 — Cancel / refund

  1. Cancelga ruxsat status va fulfillmentga bog‘liq.
  2. Unpaid: rezerv release; paid-but-unfulfilled: refund flow; shipped: return/RMA keyingi faza.
  3. Refund idempotency + provider reconciliation; yakuniy pul qaytarilganini provider statusidan tasdiqlash.

F07 — Shipment

OrderConfirmed → fulfillment request → shipment per warehouse/seller → courier assignment → picked_up → in_transit → delivered. Bir orderda bir nechta shipment; order delivered faqat biznes qoidaga muvofiq barcha zarur shipmentlar yakunlanganda.

F08 — Notification va Analytics

OrderConfirmed event → alohida consumerlar: Notification xabar yuboradi, Analytics agregatni yangilaydi. Notification xatosi order transactionini rollback qilmaydi. Retry + DLQ + dedup.
